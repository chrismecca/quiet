= Contributing to quiet

quiet-core and the canonical palettes are stable.  `docs/versioning.adoc`
defines what a quiet version covers and which changes are breaking.

The project values reproducibility, restraint, and evidence over palette
preference.

== Repository conventions

Project prose is written in AsciiDoc.

Analytical report sources are written in Org mode and exported to PDF.

Markdown files are not used.

Go is the reference implementation for quiet-core validation and
generation.

Generated and tool-managed files should remain conventional for their
respective tools.  Project conventions should not be forced into formats
that do not naturally support them.

== Naming

The project, its adaptations, and its specification have one name each,
written in lowercase everywhere, including at the start of a sentence:

----
quiet
quiet-day
quiet-night
quiet-core
----

The same string is used in prose, file names, host theme names, package
names, and palette data.  Host theme pickers therefore show `quiet-day` and
`quiet-night`.

Semantic roles are capitalized in prose and lowercase in code and data:

----
prose:  Ink on Field, Mineral, Selection, Wash
code:   ink, field, mineral, selection, moss-wash
----

The capital marks a semantic role rather than an ordinary word.

== File identification

Human-authored source files use an SCCS-style identification string where
the file format permits comments:

----
@(#)quiet / <type> / <repo-relative-path> / YYYY-MM-DD
----

For example:

[source,go]
----
// @(#)quiet / go / internal/color/srgb.go / 2026-10-16
----

The identification line is normally the first line of the file.

When a format requires a leading interpreter, magic, or file-local
directive, that required line comes first and the quiet identification
follows immediately.

The date records the last intentional semantic revision of the file.  It
is not changed for formatting-only edits.

Generated and tool-managed files do not receive manually maintained
identification strings.

Examples include:

* JSON data;
* `go.mod`;
* `go.sum`;
* generated PDFs;
* generated theme artifacts.

The standard `LICENSE` file is also left unmodified so that license
identification tools can recognize it without project-specific decoration.

== Go implementation style

Code should make invariants and failure modes explicit.

Comments should explain:

* why a calculation or constraint exists;
* what representation or units a value uses;
* where numerical constants originate;
* where precision, gamut, or quantization boundaries occur;
* assumptions that a future maintainer could otherwise violate.

Comments should not merely restate syntax.

Exported identifiers should have Go documentation comments.

Color-space conversions must not silently clip or gamut-map colors.
Gamut mapping is a design decision and must remain explicit.

Quantization to 8-bit sRGB is an export operation, not part of continuous
color calculations.

Numerical behavior that is important to quiet should have a frozen test
fixture derived independently of the implementation under test.

Dependencies should be added when they materially improve correctness or
maintainability, not merely to avoid implementing small, stable,
well-specified primitives.

== Before submitting a change

Run:

----
make check
----

A change should not introduce:

* formatting failures;
* missing file-identification headers;
* `go vet` failures;
* test failures;
* quiet-core validation failures;
* generated artifacts that differ from current generator output.

`make lint` runs staticcheck and actionlint at pinned versions.  Its first
run downloads them.

Notable changes are recorded in `CHANGELOG.adoc` under `Unreleased`.
Add that section above the newest release when it is missing.

== Continuous integration

[cols="1,3"]
|===
| Workflow | Runs

| `check`
| On every push to `main` and every pull request: `make check`,
  `make lint`, and regeneration of every port on amd64 and arm64, and of
  the Terminal.app profiles on macOS.  Fails if any committed artifact
  differs.

| `hosts`
| Weekly, and on pull requests that change ports: the port tests against
  current releases of each host application, failing if any test skips.
  JetBrains IDEs are left to local runs.

| `release`
| On a version tag: see *Releases*.
|===

Workflow actions are pinned to commits, and Dependabot proposes updates
monthly.

== Releases

A quiet version covers the whole repository.  `docs/versioning.adoc`
decides whether a release is major, minor, or patch.  To release:

. Rename the changelog's `Unreleased` section to `== VERSION (DATE)`,
  with any breaking changes first under `=== Breaking`.
. Set `Version` in `internal/release/release.go`, the `version` in
  `ports/vscode/package.json`, and the `Version` header in
  `ports/emacs/quiet-themes.el`.  Tests fail until all three agree with the
  changelog.
. Run `make generate` and `make check`.
. Merge, then tag the merge commit `vVERSION` and push the tag.

The tag starts the `release` workflow.  It checks that the tag names
`Version`, runs every check, and publishes a GitHub release with the
changelog section as its notes and the VS Code and JetBrains packages
attached.  Then publish to each channel in `docs/distribution.adoc`.

== Canonical colors

The canonical quiet anchors are intentionally conservative.

A passing canonical anchor should not be changed solely because another
color is aesthetically preferred.

A proposed anchor change should identify a concrete reason, such as:

* a failed specification constraint;
* an accessibility problem;
* a reproducible implementation problem;
* independent user-testing evidence;
* a documented inconsistency in quiet-core.

When possible, changes should minimize perceptual movement from the
existing canonical value.

== Semantics

Consequential interface meaning must not depend on hue alone.

Color may organize information, but state and meaning should also be
communicated through text, shape, iconography, position, typography, or
another non-color cue when the distinction is consequential.

== Day and Night

quiet-day and quiet-night are adaptations of the same semantic system.

They are not required to be mathematical inversions or to preserve
identical perceptual prominence ordering.

Changes should preserve semantic role, recognizable color-family
identity, readability, and the restrained character of quiet.

== Reports

Reports have three parts:

----
reports/src/    authored Org sources
reports/data/   Org tables generated by `quiet report`
reports/pdf/    published PDFs
----

Every number a report cites comes from `reports/data`, which the reference
implementation generates.  Report analysis is written in Go, like the rest
of the project.  The test suite fails if the committed tables differ from
current output, so the evidence cannot drift from the palettes.

Regenerate the tables with:

----
make report-data
----

`make generate` also regenerates them.

Export the PDFs with:

----
make reports
----

PDF export requires GNU Emacs and LuaLaTeX, so continuous integration
checks the tables but not the PDFs.  Embedded dates are pinned to the last
commit, so exporting unchanged sources reproduces the PDFs byte for byte.

Commit the regenerated PDFs together with any change to the sources or
tables they include.

== Experimental work

Scratch experiments do not automatically belong in the repository.

Promote an experiment into the project when it produces a specification
decision, reproducible test, useful reference data, or other durable
evidence.

== Philosophy

The interface should become scenery.

Color is allowed to organize.  It is not allowed to shout.
